# ADR 0003: Database conventions and the regional hierarchy

- **Status:** Accepted
- **Date:** 2026-11-21

## Context

The platform starts with Ratnagiri and Raigad districts (Maharashtra) but must support more
states and districts later without schema changes. All user-facing names are shown in Marathi,
English and Hindi. Location search ("hospitals near Dapoli") needs spatial indexes.

## Decisions

### Table conventions (all tables)

- **Primary keys:** `uuid`, generated by PostgreSQL (`gen_random_uuid()`). UUIDs avoid
  enumerable IDs in public URLs and allow offline/mobile-created records later. (UUIDv7 would
  index better; revisit with PostgreSQL 18's native `uuidv7()`.)
- **Timestamps:** `created_at` / `updated_at` as `timestamptz`, defaulting to `now()`.
  `updated_at` is maintained by a database trigger (`set_updated_at()`), so it is correct even
  for changes made outside the ORM (seed scripts, admin SQL).
- **Constraint names:** deterministic via the SQLAlchemy naming convention, for reviewable
  migrations.
- **Soft deletion:** reference data (regions, categories) uses `is_active`, meaning "hidden,
  but still referenced". User content (businesses, reviews) will use `deleted_at` in later
  sprints. Hard deletes of referenced rows are blocked by `ON DELETE RESTRICT`.

### Regional hierarchy

- **One table per level:** `countries → states → districts → talukas → villages`, each with
  a `NOT NULL` foreign key to its parent. Fixed levels match Indian administration, make
  queries and authorization ("district admin may only manage rows in their district") simple,
  and keep each level's specific columns typed.
- `villages` covers villages, towns and cities (`kind`): the brief's "Village / City" level.
- **Slugs:** lowercase ASCII (`^[a-z0-9]+(-[a-z0-9]+)*$`), unique **within the parent**
  (two talukas may share a village name). Used for SEO URLs such as `/mr/ratnagiri/dapoli`.
- **Official codes:** nullable, unique `lgd_code` (India's Local Government Directory) on
  district, taluka and village, plus ISO codes on country/state. They are populated only from
  an authoritative import, never guessed.
- **Geometry:** nullable `centroid geography(Point, 4326)` on district, taluka and village with
  GiST indexes, for distance queries in metres. Boundaries (polygons) are deferred until an
  authoritative boundary source is chosen.
- Nothing in the schema or code references Ratnagiri or Raigad; they exist only as seed data.

### Localized names

Columns per language: `name_en` (**required**), `name_mr` (**required**: Marathi is the
official language of the region), `name_hi` (**nullable**).

- Chosen over JSONB or a translation table: typed, `NOT NULL`-enforceable, simple to index
  for search (trigram indexes per column in Sprint 3), and the language set is fixed by the
  product. Adding a language is a migration, which is acceptable.
- `name_hi` is optional because Hindi spellings of local place names vary. For **place
  names**, the API will fall back `hi → mr → en`, since Devanagari Marathi is readable by Hindi
  speakers. Missing translations are never machine-invented.
- `CHECK` constraints reject blank names.

### Seed data

- Reference regions are loaded by an idempotent command (`python -m app.seed`) from a
  validated JSON file (`app/seed/regions.json`), not by migrations: migrations change
  **structure**, seeds manage **data**, and production data may diverge.
- The seed upserts by natural key (parent + slug) and never deletes.
- Initial content: India → Maharashtra → Ratnagiri (9 talukas) and Raigad (15 talukas), each
  taluka's headquarters town, and a few well-known coastal/tourist places. Coordinates, LGD
  codes and Hindi names are **left empty** until verified against official sources.

## Consequences

- New districts and states are data changes only.
- Queries joining four levels are verbose; read APIs will expose flattened views as needed.
- Seed content must be reviewed against LGD before production launch (tracked in the
  checklist).
